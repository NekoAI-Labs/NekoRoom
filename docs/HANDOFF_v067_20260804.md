## 1. 当前结论：不要把当前 APK 当作可发布版本

v0.6.7 已完成 ASR/TTS 模型选择、音色选择、导入 Live2D 删除、性能面板等主功能的代码接入；
但当前安装到真机的 v0.6.7 release APK 存在**启动即闪退**的 P0 回归，尚未修复验证，禁止继续发布。

根因已经定位，不是 TTS、Live2D、背景或 AudioTrack：

1. `LlmChatActivity.bootstrap()` 在应用启动时会执行 `asr.prepare()`，所以即使用户没有点击麦克风，已下载的 ASR 也会预加载。
2. 默认 ASR 1.2 是 Zipformer2；`ChatAsrController.buildConfig()` 却把 `modelType` 写死为 `"zipformer"`。
3. Sherpa 因而按旧 Zipformer 读取 `attention_dims`，而新模型只有 `query_head_dims`/`value_head_dims`；native 宏调用 `exit(-1)`，进程退出后 Android 图形线程才跟着报 `pthread_mutex_lock called on a destroyed mutex`。

典型日志：

```text
MoeAvatar.Chat: [语音输入加载中] 初始化语音输入…
sherpa-mnn: 'attention_dims' does not exist in the metadata
FORTIFY: pthread_mutex_lock called on a destroyed mutex
Fatal signal 6 (SIGABRT)
```

**P0 修复建议：** 不要按文件名分支，也不要重做 JNI。将 `ChatAsrController.kt` 中
`OnlineModelConfig.modelType = "zipformer"` 改为留空/自动探测，让 sherpa-mnn 从 MNN metadata
读取 `model_type`。已独立验证：同一套 1.2 MNN 在 host C++ demo 中不显式传 `modelType` 可以自动识别为
`zipformer2` 并完成推理。修改后须先连续冷启动至少 3 次，再测麦克风。

> 旧 ASR 1.1 能工作，是因为它恰好就是 `zipformer`；新 1.2 被设为默认后才暴露出旧硬编码。
> TTS v1.3 接入与该崩溃只是时间上重叠，不是直接因果。

- 设备信息在 `PerformanceDeviceInfo.kt`，性能记录在 `perf/PerformanceRecordStore.kt`，设置绑定在

- iQOO Neo5s 的“打开后不显示性能信息”尚无可复现日志，**未确认是专属机型问题**。排查顺序：
  1. 确认开发者模式已开启；2. 确认“显示性能信息”和“性能日志”状态；3. 看 `MoeAvatar.Chat` 是否写入性能记录；
  4. 检查性能面板弹窗是否因设备信息格式化异常提前返回。`PerformanceDeviceInfo` 已有 `runCatching` 防御，

## 4. MNN、并发与电话模式的边界

### 4.1 当前实现

- LLM、TTS、ASR 都链接同一套 `libMNN.so` / `libMNN_Express.so`。
- `MnnGlobalLock` 目前串行化 native MNN 调用，避免多个 runtime 同时操作全局 executor/allocator 导致 SIGSEGV。
- 这提高稳定性，但 TTS 一整句推理可持锁 1–2 秒，会让 ASR decode 延迟；AudioRecord 采集已经拆成单独线程 + 12 秒 PCM 队列，减少首词丢失。

### 4.2 不要贸然“全部解锁”

“LLM 文本流式输出时 TTS 也应继续播放”是产品目标，但不等于可以让三个 MNN 推理并发。当前 MNN runtime
是否可安全多 session 并行没有端到端证明。后续若要优化：优先只缩小锁的范围、让 TTS 分句/分 chunk，
并每次在真机连续压力测试后再推进；不要直接移除锁。

### 4.3 电话模式

- 输入：`VOICE_COMMUNICATION` + 系统 AEC/NS/AGC（设备支持与否必须看日志）。
- 输出：`SpeechQueue` 使用 `USAGE_MEDIA` + `CONTENT_TYPE_MUSIC`，不能改成通话播放路径，否则会小声、发闷。
- 当前没有 Android 公共 API 可手工向系统 AEC 注入 AudioTrack 的 PCM reference；是否有效依赖厂商 HAL。
- 实时打断依赖 `VoiceInputController`、`PhoneCallController`、`ChatAsrController` 的 20 ms 采集帧和预录音。
  调 VAD 阈值前先保留日志，避免“减少自打断”换来“用户必须大声说话”。
- 已知仍需真机回归：外放残响会偶发自打断；用户打断时首词是否完整保留；多次打断后 UI 是否稳定进入聆听。
  WebRTC AEC3 尚未接入。

## 7. 最小安全迭代流程

1. 从干净分支创建一个功能/fix 分支；先 `git status`，绝不覆盖未提交的其他 Agent 改动。
2. 先读本文件、`myrules.md`、相关模块代码和最近 commit；复杂改动先写/更新设计说明。
3. 一个功能点只改必要文件，避免同时改模型转换、JNI 和 Activity，使回归无法归因。
4. 至少执行 Kotlin/Gradle 编译；涉及模型启动、AudioTrack、JNI、R8 的改动必须真机验证。
5. 对启动回归至少测试：冷启动 3 次、模型切换一次、进入/退出电话模式一次、正常文本聊天一次。
6. 验证后立即按 Conventional Commits 提交，例如：
   `fix(asr): v0.6.7 detect zipformer model type from metadata`。
7. 更新面向用户的 `CHANGELOG.txt` 时只写用户可感知内容；内部根因、混淆、JNI、回归过程写入本交接文档或开发日志。
8. 模型、APK、日志、缓存、签名文件、API key 一律不入库；大文件放 `/mnt/d`。

## 9. 关键坑速查

- App 启动会自动 `asr.prepare()`；“用户未点麦克风”不代表 ASR 不会造成 crash。
- `OnlineRecognizer` 的 native 配置错误可能 `exit(-1)`，Kotlin 的 `runCatching` 接不住进程退出。
- 模型名不等于架构，使用 MNN metadata 或明确注册表；不要从 `medium/fp16` 推断 `zipformer/zipformer2`。
- `GetMNNInfo` 才能检查 MNN metadata；`strings` 不能作为结论。
- 动态 shape TTS 的 voice 是模型运行目录内的 `voices/*.json`，不是与 MNN 平铺，也不是 APK 内置资源。
- 旧模型必须保持可检测、可选择、可回退；升级 APK 不得强制删除用户模型。
- `VOICE_COMMUNICATION` 仅用于采集；TTS 播放必须保留 `USAGE_MEDIA/CONTENT_TYPE_MUSIC`。
- AudioTrack release/idle check 需 generation/lease 防竞态；不要只用 try/catch 掩盖已 release 对象。
- 不要把 MNN 全局锁直接删掉；先建立稳定性测试，再做颗粒度优化。
- 归档树和历史工作副本经常不同步；打包前先 `diff -qr`，发布 APK 必须可追溯到具体 commit。
